## Q1. Zonotope / polynomial-zonotope / constrained / hybrid-zonotope representations in manipulation (ARMTD, ARMOUR, SPARROWS and successors): where do the obstacle and object sets come from?

### Takeaway
In every Vasudevan-lab (ROAHM) reachability planner I checked (ARMTD, ARMOUR, SPARROWS, CROWS), the zonotope or polynomial-zonotope machinery describes the **robot's swept volume**. Obstacles are **assumed to be given** as zonotope or polytope over-approximations. In the experiments they are hand-placed axis-aligned cubes, or objects tracked by motion capture. None builds obstacle sets from point clouds. The only perception-driven member of the family is SPLANNING (2409.16915). It drops zonotope obstacles and instead bounds collision probability against a Gaussian Splat built from RGB images. Outside manipulation, hybrid-zonotope planners (Pangborn group) take polytopic maps or occupancy grids as input and solve MIQPs, but only for vehicles or other low-dimensional systems.

### Cited Findings

**ARMTD: "Reachable Sets for Safe, Real-Time Manipulator Trajectory Design"**: Patrick Holmes, Shreyas Kousik, Bohao Zhang, Daphna Raz, Corina Barbalata, Matthew Johnson-Roberson, Ram Vasudevan. arXiv **2002.01591** (Feb 2020), RSS 2020. VERIFIED (body read via PDF text). — [arXiv](https://arxiv.org/abs/2002.01591); [RSS proc.](https://roboticsproceedings.org/rss16/p100.html)
- Set type: an offline joint reachable set (JRS) of parameterized trajectories, each ending in a braking fail-safe. At runtime the arm's forward occupancy is built from **rotatotopes**, defined as matrix zonotopes times zonotopes, and described as "a special class of polynomial zonotopes". VERIFIED. — [PDF](https://arxiv.org/pdf/2002.01591)
- Obstacles: "We overapproximate each O by a zonotope, which is always possible for compact, bounded sets … that appear in common obstacle representations such as octrees or convex polytopes". On hardware: "The obstacles are tracked using motion capture, and treated as static in each planning iteration" (a box, a vase, a quadrotor). **No point clouds.** VERIFIED. — [PDF](https://arxiv.org/pdf/2002.01591)
- How the constraint enters: zonotope intersection test (their Lemma 8). Build a half-space representation (A_buf, b_buf) of the arm zonotope buffered by the obstacle generators. Then "X∩Y=∅ ⟺ max(A_buf y − b_buf) > 0". The arm rotatotope is sliced by the trajectory parameter k_a. Generators that cannot be sliced are moved into the obstacle buffer. The result is "sub-differentiable and provably-conservative collision-avoidance constraints on the trajectory parameters", solved with IPOPT. In other words the constraint is a nonsmooth max of affine functions evaluated at a center that is polynomial in k. It is not linear. VERIFIED. — [PDF](https://arxiv.org/pdf/2002.01591)
- Cost: constraint generation in parallel takes "approximately 10–20 ms for 20 obstacles". IPOPT takes "100–200 ms when it finds" a solution. t_plan = 0.5 s. Robot: Fetch, 7 DOF. VERIFIED. — [PDF](https://arxiv.org/pdf/2002.01591)
- Stated limitations: "may not perform in real time without parallelization, is only demonstrated on 6DOF planning problems, and has not yet been demonstrated planning around humans". Uncertainty (tracking error) is mentioned only as future work. VERIFIED. — [PDF](https://arxiv.org/pdf/2002.01591)

### Inferences
- The zonotope-family manipulation literature has a clear gap: **perceived point cloud → zonotope obstacle → reachability constraint** with perception uncertainty propagated through. ARMOUR states the sensing assumption outright and suggests treating occluded regions as obstacles, but nobody in the family closes that loop on hardware. The obstacles are mocap boxes (ARMTD) or synthetic cubes (SPARROWS, CROWS).
- "Zonotope" in this family means **robot occupancy under trajectory-parameter and model uncertainty**, not object shape. For object shape, the realistic route is point cloud → box, convex hull or MVEE → zonotope over-approximation, for example with CORA conversions. That conversion is conservative and not studied in these papers.
- WAITR's contact-wrench polynomial zonotopes are the nearest analog to a cup-tilt or spill constraint. It reasons about dynamics (friction, wrench), not object geometry.

- ARMOUR planning-time numbers and how obstacles were known in its hardware runs: the ar5iv text was truncated and I did not extract them.

- Kochdumper's 2210.10691 and ZAPP were checked at metadata level only. I did not confirm whether either includes manipulator or point-cloud experiments.

## Q2. Point cloud → convex sets (CoACD, V-HACD, superquadrics, ellipsoid/polytope fitting, convex hulls of segmented points) feeding MPC/CBF constraints

### Takeaway
There are two families. **Offline shape decomposition** (CoACD, V-HACD, CvxNet, superquadric fitting such as EMS and SuperDec) produces convex pieces or primitives but does not plan. CoACD needs a **mesh**, not a raw point cloud. **Free-space convexification** (IRIS, IRIS-NP/NP2/ZO, C-IRIS, FIRI, Splat-Nav, PolyMerge, PathCover) builds collision-free polytopes from obstacle sets or point clouds, which then become **linear constraints** for GCS, MPC or corridor planners. For manipulators, the perception-to-constraint pipelines I found that actually run go through **superquadrics** (Brunke et al. 2410.15185, 45 Hz), **MVEE ellipsoids** (VLSA 2512.11891, about 0.36 ms per step), **learned distance fields** (neural C-space barriers 2503.04929), or **Poisson safety functions** (VLPSA 2609.22462). None goes through zonotopes.

### Inferences
- CoACD and V-HACD are meant for **complete meshes of known objects**, for example a CAD model of the cup or the tray. They are a poor fit for single-view partial point clouds. For live perception, use superquadric fitting (EMS or SuperDec), MVEE ellipsoids, or the convex hull of the segmented points.
- If FL-MPC needs **linear QP rows**, the most natural pipeline is: segmented point cloud → convex hull, axis-aligned box or MVEE → (optionally) a zonotope over-approximation → per-step separating hyperplanes or support-function rows. This mirrors Splat-Nav and FIRI on the free-space side and the supporting-hyperplane DCBFs in Q4 on the obstacle side.
- Superquadrics (Brunke) and ellipsoids (VLSA) give smooth CBFs that are linear in the control input u at each step (see Q3). They are not polytopes, so they do not give the constant-row structure of GCS or IRIS.

### Gaps
- V-HACD: I found no arXiv paper and did not verify its primary reference in this pass.
- Marching-Primitives (superquadrics, CVPR 2023): not verified this pass.
- I found no published manipulator pipeline of the form "convex hull of segmented points → zonotope → reachability planner".
- Uncertainty handling: of the point-cloud pipelines, only EMS models outliers explicitly (in the fit). None propagates fit uncertainty into the constraint margin. SPLANNING and CROWS give probabilistic bounds, but for a different source of error (see Q1).

## Q3. Do any works make LANGUAGE/VLM-specified constraints set-valued (not keypoints, not Python code)? Comparison with ReKep, OmniManip, SpaTiaL/NL2SpaTiaL, SafeBimanual

**Yes, but only with smooth primitives, and only a few.** Brunke et al. (2410.15185, Schoellig lab) is the clearest precedent. An LLM outputs (object, unsafe-relation) pairs, for example (laptop, above). Each pair becomes a **superquadric unsafe set fitted to the object's point cloud, extruded in the relation's direction**, enforced as a CBF at 45 Hz on a Franka FR3, plus an LLM-gated end-effector rotation constraint for a "cup of water". VLSA/AEGIS (2512.11891) has the VLM pick the critical obstacle, then fits an **MVEE ellipsoid** to its point cloud for a CBF-QP. VLPSA (2609.22462) synthesizes Poisson safety functions from perception. **I found no work where language or a VLM produces zonotope, constrained-zonotope or polytope constraints for manipulation.** The other language-to-geometry systems output keypoints (ReKep, SafeBimanual), canonical-frame points and directions (OmniManip, CoPa), voxel value maps (VoxPoser), 2D-disk spatial logic (NL2SpaTiaL), or code/MIP (Semantic Constraint Synthesis, M³P-R1, OVITA).

### Inferences
- The gap is specific and narrow. **Language/VLM → hard, set-valued, polytope or zonotope constraints with linear rows in an MPC/QP, for manipulation (and bimanual), with perception uncertainty in the set** appears unclaimed. Brunke uses superquadric CBFs on an EE point, VLSA uses one MVEE ellipsoid on the EE, and neither uses zonotopes or linear-row polytopes or reasons about the held object's full occupancy. Caveat: this rests on about 50 targeted searches and fetches, not an exhaustive survey.
- Brunke's "cup of water above laptop / don't rotate cup" is close to this project's cup-tilt and spill setting. Any paper claiming language-to-set constraints for cup transport must cite and beat it. The obvious differences are hard versus soft rotation, held-object occupancy versus an EE point, and zonotope/linear rows versus superquadric CBF.
- The relation-extrusion trick (duplicate the cloud and push it in +z, then fit) works for any convex fitter. With a box or zonotope fitter it yields a **zonotope "relation set"** (e.g. above(laptop) = zonotope ⊕ a +z segment generator). This is a cheap, direct way to make language relations zonotope-valued.

## Q4. Which approaches keep constraints LINEAR in the decision variables (support functions / separating hyperplanes), and how do they handle rotation?

### Takeaway
Linearity is kept in two ways. **(a) Move the convexity into the space being planned.** GCS, IRIS and C-IRIS build polytopes in configuration space (C-IRIS in a **rational parameterization**, so rotations are certified by SDP). The planner then sees fixed linear rows, and rotation is absorbed offline. **(b) Re-linearize every step.** Supporting or separating hyperplanes from exact closest points give linear DCBF/MPC rows (Liu, Huang & Belta 2603.05916). CBF-QPs (VLSA, Brunke, Wei et al.) are linear in u at each step. The zonotope-reachability planners (ARMTD, SPARROWS, CROWS) handle rotation **exactly but nonlinearly**: rotatotopes or polynomial zonotopes over cos/sin of the joint angles, sliced by the trajectory parameter. This yields nonsmooth or polynomial constraints solved by IPOPT at 0.14 to 0.45 s per plan. Brunke treats orientation as a linearized log-map bound turned into a soft cost.

### Cited Findings
- **ARMTD rotation**: per-joint rotations are matrix zonotopes over cos/sin of the JRS. Their product with a link zonotope is a rotatotope ("A matrix zonotope times a rotatotope is a rotatotope"). The collision constraint is max(A_buf·eval(V_slc, k) − b_buf) > 0, which is affine in the sliced point but polynomial in k, and nonsmooth because of the max. Generators that cannot be sliced (rotation uncertainty) are treated conservatively by buffering obstacles. VERIFIED. — [PDF](https://arxiv.org/pdf/2002.01591)
- **SPARROWS**: SDF(O, c̄(k)) > r̄(k). This is a nonlinear exact signed distance from a sphere center to a zonotope, and it requires precomputed zonotope vertex enumeration. VERIFIED. — [arXiv HTML](https://arxiv.org/html/2402.08857v1)
- **C-IRIS**: polytopes "in a rational parameterization" of C-space, certified collision-free by SDP. The obstacles only need to be convex in task space. VERIFIED (abstract). — [arXiv](https://arxiv.org/abs/2302.12219v2)
- **IRIS-NP**: separating hyperplanes are found by NLP in C-space. The resulting polytope gives linear constraints to GCS. SUMMARY. — [arXiv](https://arxiv.org/abs/2303.14737v1)
- **Liu, Huang, Belta**: "Iterative Convex Optimization with Control Barrier Functions for Obstacle Avoidance among Polytopes", arXiv **2603.05916** (6 Mar 2026). It "construct[s] linear discrete-time control barrier function (DCBF) constraints by deriving supporting hyperplanes from exact closest-point computations", inside a convex MPC with "millisecond-level solve times". The abstract does not address rotation. VERIFIED (abstract). — [arXiv](https://arxiv.org/pdf/2603.05916)
- **Wei et al. 2410.19159**: "transform nonconvex safety constraints into linear constraints by differentiable optimization" (a HOCBF over convex primitives). VERIFIED (abstract quote). — [arXiv](https://arxiv.org/html/2410.19159)
- **Gao, Messerer, van Duijkeren, Houska, Diehl**: "Real-Time-Feasible Collision-Free Motion Planning For Ellipsoidal Objects", arXiv **2409.12007** (18 Sep 2024). It uses a "parametric over-approximation of the Minkowski sum, which can be made tight in any given direction". This is effectively a direction-parameterized support-function bound. VERIFIED (abstract). — [arXiv HTML](https://arxiv.org/html/2409.12007v2)
- **Fan, Murgovski, Liang**: "Efficient optimization-based trajectory planning", arXiv **2312.17440** (29 Dec 2023). Objects and obstacles are unions of convex polytopes and ellipsoids. It uses the "hyperplane separation theorem to formulate differentiable separating constraints" and the "S-procedure … to formulate smooth containing constraints". VERIFIED (abstract). — [arXiv HTML](https://arxiv.org/html/2312.17440v2)
- **Separating-hyperplane drawbacks**: one search summary states that hyperplane-separation formulations "introduce additional decision variables, suffer from numerical divergence, and yield dual-linear constraints whose gradients can be discontinuous". SUMMARY (search snippet; I could not attribute it to a specific paper). — [search context: 2603.05916](https://arxiv.org/pdf/2603.05916)
- **VLSA**: the ellipsoid CBF enters "ḣ(x) ≥ −α(h(x))", which is affine in u. VERIFIED. — [arXiv HTML](https://arxiv.org/html/2512.11891v2)
- **Brunke rotation**: ψ = J_o(q)u·Δt makes the orientation bound affine in u at each step, but it is "softened" into a cost to avoid infeasibility. VERIFIED. — [PDF](https://arxiv.org/pdf/2410.15185)
- **Hybrid zonotopes**: nonconvex free space stays "linear plus binaries" (MIQP), and for some forms the convex relaxation is tight. VERIFIED (abstract). — [arXiv](https://arxiv.org/abs/2411.01286)

### Inferences
- These points are my own reasoning, not sourced claims. For an obstacle zonotope Z = ⟨c, G⟩ and a unit direction n, the support function is h_Z(n) = nᵀc + ‖Gᵀn‖₁. This is a standard identity, not re-sourced in this pass. If n is fixed at each MPC step (for example, the previous closest-point normal, as in 2603.05916), the clearance row nᵀp(x) ≥ h_Z(n) + h_{robot}(−n) + margin is **affine in the point p**. It stays linear in the acceleration decision variable once p is propagated through FL-MPC's exact double-integrator prediction and the per-step kinematic Jacobian. This is the same kind of linearization FL-MPC already uses for arm-arm clearance rows.
- Rotation enters in only two places. The first is the **robot or held-object body set**: a rotated zonotope RZ = ⟨Rc, RG⟩ stays a zonotope for a fixed R, so a per-step linearization of R(q) keeps rows linear, with a conservative error buffer like ARMTD's non-sliceable-generator buffer. The second is the **direction choice n**. Neither forces an NLP if each step is accepted as a convex QP. Exact guarantees over the horizon still need a buffer of the ARMTD or polynomial-zonotope type.
- For a cup-tilt constraint, no source suggests a set-valued encoding better than an orientation bound. Brunke uses a linearized log-map, which is equivalent to a per-step linear row. Spill remains geometry-blind, consistent with AGENTS.md.
